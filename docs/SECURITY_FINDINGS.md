# Проверка безопасности перед релизом 1.0

Проверено 8 ноября 2026, Asia/Qyzylorda. Основание: требования владельца к единственному администратору и текущий commit `26b6f022d16419262fd3d444b7d90fd82a0b17ff`. Это аудит готовности, а не подтверждение завершения новой системы входа.

## Проверка секретов

Без вывода значений проверены 102 отслеживаемых файла текущего дерева и 465 достижимых объектов полной локальной истории, включая 68 коммитов. Репозиторий не shallow. Сканер читал содержимое Git blob, сопоставлял стандартные формы Telegram bot token, Supabase secret key/service-role JWT, GitHub PAT, ключей провайдеров и закрытых ключей; JWT классифицировались по роли без печати токена. Дополнительно проверялись 64-символьные SHA-256 рядом с обозначением административного пароля.

Границы сканирования: проверено текущее отслеживаемое дерево и достижимая история локального клона, без обфусцированных/составных значений, недостижимых объектов, форков, чатов, приватных хранилищ и полного архива CI-логов. SF-02 описывает различие с новым правилом владельца, а не найденную возможность гостя повысить себе права. Текущий `account.save` требует действующую административную сессию; самостоятельной регистрации в этом endpoint нет. Реальное число дополнительных административных аккаунтов в рабочей БД на этом этапе не запрашивалось.

SF-02 дополнительно воспроизведён изолированно: in-memory подмена `fetch` вернула действующую сессию не-владельца с серверной рольюadmin; запрос `account.save` создал ещё одну рольadmin и получил200. Подмена принимала только адрес `https://isolated.invalid`; реальных запросов к БД и сетевых записей не было. Проба не сохраняла пароль, токен или хеш в файлы и не выводила их значения.

## Проверенные границы серверного доступа

| Точка | Текущая проверка |
| --- | --- |
| `uniflow-api / state` | Без токена возвращается гостевая проекция. С токеном вызывается `actor`; аккаунты и версии возвращаются только серверной ролиadmin (`backend/uniflow-api.mjs:90–119`, `:208–229`). Привязки к email владельца пока нет |
| `uniflow-api / account.save` | Только серверная рольadmin; допускается создание ещё одной ролиadmin (`:243–313`) |
| `uniflow-api / password.change` | Требуется действующая сессия и текущий пароль; смена хеша и отзыв сессий выполняются SQL-RPC (`:315–344`) |
| `uniflow-api / mutate`, включая импорт | Требуется сессия; модель проверяет права на операцию (`backend/core.mjs:474`), импорт отдельно требуетadmin (`backend/uniflow-api.mjs:369–397`); атомарная запись через `uf_commit` |
| `uniflow-api / rollback` | Толькоadmin и текущая ожидаемая ревизия (`backend/uniflow-api.mjs:348–367`) |
| `uniflow-api / logout`, `logout.all` | Сессия проверяется до обработки. Общий отзыв SQL-RPC удаляет обе генерации сессий встроенногоadmin (`:231–240`; migration`:28–35`) |
| `schedule-admin / save` | Сначала проверка действующей legacy-сессии, затем запрет записи410. `login` пока сохраняется |
| `uniflow-calendar` | Только GET/HEAD/OPTIONS, публичные учебные поля, без административных записей (`backend/calendar.mjs:21–26`, `:76–89`) |
| Прямой Data API / RPC | SQL включает RLS и отзывает доступ клиентских ролей к административным таблицам; служебные функции — `SECURITY INVOKER`, EXECUTE толькоservice_role (`backend/uniflow-schema.sql:7–10`, `:28–29`; migration`:25–26`, `:34–35`, `:49–50`, `:73–74`) |

`service_role`/секретный серверный ключ — доверенная привилегированная граница, а не средство входа владельца в интерфейс. Ключ не должен попадать в браузер. Публичный URL проекта и publishable key не дают административную роль сами по себе. CORS и скрытая ссылка также не заменяют серверную авторизацию.

## Выполненная проверка и пределы результата

Команда `node --test tests/backend-http.test.mjs tests/backend-model.test.mjs tests/backend-conflicts.test.mjs` выполнена8ноября: **31passed,0failed,0skipped**. Проверены, в частности, запрет подмены роли гостем, отсутствие записи без сессии и с истёкшей сессией, границы преподавателя, публичная проекция без приватных списков, атомарный отзыв/смена пароля, лимитер, конфликт ревизий и запрет записи старым редактором. HTTP-проверки используют локальные подмены БД/fetch; боевых запросов записи не было.

Эти31проверка подтверждают существующую модель ролей. Они **не доказывают** owner-onlyemail, OTP/TOTP, bootstrap, одноразовые recovery-коды или доставку уведомлений: таких механизмов пока нет. Нужны отдельные серверные негативные сценарии для не-владельца, даже если его аккаунту ошибочно присвоено значениеadmin.

Новый пароль владельца, содержимое серверных секретов и реальные сессии не читались; миграции, ротации, удаление данных, отзыв реальных сессий и переписывание истории не выполнялись. Реальный положительный вход владельца с2FA и ручные физические устройства этим аудитом не проверены.
