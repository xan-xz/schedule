## Первая настройка — один раз

1. После проверки Auth-настроек выше откройте `/schedule/admin/`. В состоянии «Настройка владельца» нажмите **«Отправить приглашение владельцу»**. Сервер выбирает только `arappayevv@gmail.com`, игнорирует присланный клиентом адрес и ограничивает повторные запросы. Кнопка не даёт прав посетителю и не отправляет приглашения на произвольную почту.
2. Проверьте входящие и «Спам». Подтвердите приглашение в действующем 15-минутном окне UniFlow одним способом: откройте кнопку письма для первичной настройки **либо, не открывая её, скопируйте адрес кнопки** в поле приглашения и нажмите «Подтвердить приглашение». При первичной настройке страница принимает native Auth fragment и сразу убирает credentials из адреса; вставленную ссылку сервер только разбирает для своего Supabase-проекта, не загружает произвольный URL. Если кнопку уже открыли, но переход завершился ошибкой, native Auth мог успеть использовать ссылку: повторная вставка старого адреса не восстановит её. Исправьте настройки redirect и запросите новое письмо после указанной паузы.
3. Самостоятельно задайте новый уникальный пароль: **не менее 12 Unicode-символов и не более 72 байт UTF-8**, затем подтвердите его. Верхняя граница — 72 ASCII-символа, 36 обычных кириллических букв или 18 четырёхбайтовых emoji; для смешанного пароля считается сумма байтов, минимум 12 символов сохраняется. Пароль не обрезается автоматически. Сохраните его в своём менеджере паролей. Пароль не является Supabase API key, Telegram token или общим env-секретом. Прежний пароль, чей verifier остался в git, повторно не используйте.
4. Добавьте аккаунт в приложение-аутентификатор по QR или секрету на странице. **QR создаётся локально**, без внешнего QR-сервиса. Введите шестизначный TOTP-код. Не пересылайте QR/seed и не сохраняйте их в issue, отчёте или общих Secrets.
5. Сохраните **10 резервных кодов** в личном менеджере паролей либо безопасной offline-копии и отметьте сохранение. Список показывается один раз; на сервере хранятся хеши. Каждый код однократный.
6. Только после полного подтверждения сервер активирует владельца. Он закрепляет owner UID и утверждённый TOTP-factor; старые административные сессии отзываются. Повторное использование email-сессии настройки и запуск setup после активации не предоставляют доступ.

Числовой OTP и ссылка-кнопка — варианты подтверждения почты, а не отдельные обходы остальных факторов. Срок native auth-письма задаётся в Supabase отдельно; сервер UniFlow дополнительно проверяет своё окно, одноразовость и владельца. Истёкшее или уже использованное приглашение не чинится пересылкой секрета агенту.

Если завершение setup произошло на сервере, а ответ со списком резервных кодов потерялся, войдите обычным способом с паролем, свежим подтверждением почты и TOTP, отметив **«Обновить резервные коды»**. Новый набор показывается один раз; прежний становится недействительным. Эта возможность не сбрасывает пароль и не заменяет 2FA.

## Обычный вход и выход

1. Введите пароль владельца. Email фиксирован сервером; поля для назначения другого администратора нет.
2. Сервер отправит подтверждение только на почту владельца. Введите код **либо, не открывая кнопку письма, скопируйте её ссылку** в «Код или ссылка из письма» в той же вкладке начатого входа. Автоматический native fragment предназначен для первичного setup; открытие кнопки при обычном входе может использовать ссылку и потерять текущую цепочку подтверждения. В таком случае начните новый вход и получите свежее письмо с учётом ограничений отправки.
3. Введите TOTP из своего приложения. Пароль, почта и TOTP должны относиться к одной серверной цепочке входа. Один фактор административной сессии не выдаёт.

Access token действует 15 минут, refresh ротируется, абсолютный срок сессии — 1 час без продления. Клиент хранит оба токена только в памяти; закрытие или перезагрузка страницы требует нового входа. Ни localStorage/IndexedDB, ни service worker не должны сохранять эти credentials. При отсутствии сети вход и административная запись недоступны.

**«Выйти на всех устройствах»** очищает локальную сессию даже при ошибке сети. Если сервер не подтвердил отзыв, страница сообщает об этом: нельзя считать остальные устройства вышедшими. После восстановления связи повторите вход и выход везде. Защищённое чтение состояния подходит для проверки отзыва; боевую правку расписания для этого делать не требуется.

## Потеря TOTP и забытый пароль — разные случаи

Если пароль известен, но приложение-аутентификатор недоступно: начните обычный вход, подтвердите почту, выберите **«Нет доступа к приложению»**, введите один резервный код и пароль ещё раз. Сервер отзовёт прежние сессии и разрешит только подключение нового TOTP. Новое приложение необходимо подтвердить до доступа в управление; затем сохраняется новый набор из 10 кодов. При временной ошибке следуйте сообщению страницы и повторяйте текущий шаг: код не должен расходоваться повторно при возобновлении той же операции.

**Публичного сброса забытого пароля после активации пока нет.** Резервный код восстанавливает второй фактор, а не пароль. Первичный setup после активации закрыт. Если потеряны пароль, почта либо все средства восстановления, требуется отдельная процедура подтверждения владельца и восстановления; не правьте `password_hash` вручную, не ищите исходный пароль в Secrets и не отправляйте пароль/коды агенту. Из хеша исходный пароль извлечь нельзя.

## Что проверяет сервер

Закреплённые owner UID/email, подтверждённую почту, активную native Auth-сессию с утверждённым проверенным TOTP-factor и AAL2, сроки и отзыв приложения. Native JWT сам по себе, клиентские role/email/user_metadata и Telegram chat ID прав не дают. Auth-пользователь владельца только email: БД запрещает `phone` и `phone_change`; адаптер и SQL повторно проверяют это. SMS, WhatsApp и OAuth не считаются подтверждением почты.

В опубликованном коде старый `admin` login, смена его пароля и legacy save закрыты ответом 410; ответ старого login проверен на действующем origin. Дополнительная роль admin запрещена API и БД; старые административные токены не читают и не изменяют данные, им оставлен только отзыв собственной сессии. Наличие старой страницы или сохранённого токена не возвращает доступ.

Входы, ошибки и восстановление пишутся в закрытый audit с минимальными данными. Автоматические оповещения о входах в Telegram/почту пока не реализованы. Полноценный Telegram-клиент — будущий [этап 7Б](TELEGRAM_CLIENT_PLAN.md), не часть действующего входа.

## Исторический verifier и откат

Исторический SHA-256 verifier остаётся в git; новый пароль должен быть уникальным. Очистка истории не выполнена и требует отдельного согласования: refs, приватный mirror, проверка удаления, окно force-push, клоны/форки, теги и release manifests. Не уничтожать единственную проверенную копию отката; чужие кэши могут сохранить историю.

Подготовлен приватный backup с ограниченным ACL вне workspace; содержимое и credentials не публикуются. Репетиция миграции и отката до активации не доказывает безопасный возврат старого входа после owner cutover. После активации восстановление старого password-only endpoint нельзя использовать как штатный rollback. Точный статус backup/checksum/SQL и развёртывания — в отчёте этапа.
