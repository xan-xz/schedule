Статус на 8 ноября 2026: **запланировано, не реализовано и не развёрнуто**. Этот документ сохраняет полное дополнение владельца о Telegram (`a0d35d37-2225-4356-9dd4-5c0d0e0b1066`) и уточняет будущую реализацию. Наличие плана не означает, что бот, Mini App, уведомления или привязка уже работают. Сейчас выполняется этап 1: единственный владелец, одноразовая установка пароля и 2FA. Настоящий токен, webhook и доставка в рамках этого документа не настраиваются.

Дополнение заменяет Telegram-часть этапа 7 исходного ТЗ и вводит этап 7Б. Почта и Web Push остаются отдельными требованиями. В таблице RELEASE_1_PLAN уведомления выделены в PR 11; номер 7Б относится к исходному ТЗ и не переставляет текущие PR.

## Цель и границы

Сайт и бот — два клиента одной системы: одна Supabase БД, одни сущности, права, ревизии и серверная валидация. Студент сможет пользоваться только ботом, только сайтом или обоими. Открытие сайта не требуется для просмотра расписания, заданий группы, напоминаний и поддержки из бота. Владелец сможет выполнять ограниченный набор текущих административных действий из бота после обычной серверной авторизации.

Реализация зависит от завершённого owner auth этапов 1–2, единственного источника данных, общего слоя чтения/записи и поддержки. Не создавать параллельное расписание, отдельного Telegram-администратора, новый путь выдачи ролей или копию правил расписания. Секреты — только на сервере; платные сервисы и платные рассылки автоматически не подключать.

## Общая архитектура и данные

- `telegram-webhook`: серверная Edge Function, HTTPS webhook вместо клиентского long polling. Проверять `X-Telegram-Bot-Api-Secret-Token` до обработки JSON, допустимые типы update, размер тела, структуру и отправителя. IP не считать самостоятельным доказательством подлинности. Постоянный секрет заголовка не заменяет проверки прав.
- Общий серверный service layer используется сайтом и webhook. Единые функции «сейчас / дальше / окно», ISO-чётности, Asia/Almaty, периодов семестра, каникул и разовых изменений. Единые проверки занятости группы, преподавателя и аудитории, справочников и ожидаемой ревизии. Бот вызывает эти функции, а не собирает независимый JSON расписания.
- `telegram_users`: `telegram_user_id`, `chat_id`, group/subgroup, язык, тема, уведомления, тихие часы, created/last_seen, статус подписки. Поддержать большие Telegram ID без потери точности; username и display name не являются идентификатором или правом доступа.
- `telegram_link_codes`: хеш случайного кода, назначение, срок, отметка использования и минимальные данные привязки. Отдельные назначения student-device, owner-bind и owner-step-up; атомарный consume, TTL 10 минут для обычной привязки. Открытые коды не хранить и не логировать.
- `telegram_owner`: связь только с закреплённым owner UID; ограничения БД запрещают второго владельца и замену владельца обычной командой. Сам `chat_id` не даёт административной сессии.
- `bot_audit_log` и общий `audit_log`: источник `telegram`, actor, тип действия, результат, время и идентификатор ревизии; без токенов, TOTP, полного initData и лишнего содержимого обращений. `update_id`/delivery keys уникальны для идемпотентности.
- Короткие bot-admin sessions, device bindings и очередь уведомлений могут потребовать отдельных закрытых таблиц. Все новые таблицы — с минимальными grants и deny-by-default RLS; сервисный ключ используется только после проверок actor/scope. Прямого публичного доступа к чатам, связям и обращениям нет.
- `SupportTicket`, ответы и статусы общие для обоих клиентов, с полем источника. Фото проверяются по размеру/типу и хранятся приватно; скачивание не раскрывает Telegram token, чужой file/chat ID или постоянную публичную ссылку.

До миграции: резервная копия, dry-run, индексы, ограничения и проверенный откат. Не читать и не переносить пароли/сессии в публичные artifacts. Обновить политику конфиденциальности: какие Telegram данные нужны, для чего и как удалить.

## Двусторонняя привязка и настройки

1. Сайт → бот: «Ещё → Telegram → Открыть бота», `t.me/<bot>?start=<одноразовый_код>`. Код передаёт текущие группу, подгруппу, язык и тему, действует 10 минут и используется один раз. Не помещать в ссылку постоянную сессию, bot token или чужие данные.
2. Бот → сайт: «Открыть сайт» ведёт на канонический `/schedule/` с публичным `?g=<код группы>` и согласованными параметрами подгруппы. Для изменения приватных настроек требуется проверенная связь устройства либо серверно проверенный Mini App context; один query-параметр прав не даёт.
3. Первый `/start` без связи: выбрать группу поиском и inline-кнопками, подгруппу А/Б/Обе и ru/kk/en. Далее сразу «Сегодня» без повторного выбора. При открытии сайта из связанного бота не спрашивать группу заново.
4. Серверная запись связи Telegram ↔ устройство — источник синхронизации группы, подгруппы, языка и времени напоминаний. Регистрация студента не требуется; анонимное устройство подтверждается отдельной непредсказуемой capability, не произвольным присланным device ID. Проверять версию настроек и отзыв связи.
5. На сайте «Отвязать Telegram», в боте `/unlink`: атомарно отозвать связь/коды/доставку согласно выбранному scope, не удалять локальные задания сайта. `/delete_me` после подтверждения удаляет данные подписчика и закрывает очередь его уведомлений с документированной минимальной политикой хранения audit.

Решение для будущего DECISIONS.md: личные задания сайта остаются локальными на конкретном устройстве и не синхронизируются автоматически. В боте по умолчанию доступны задания группы и отдельные личные заметки, закрытые scope конкретного `telegram_user_id`; это не копия локальных заданий сайта. Более полные серверные «задания в боте» включаются владельцем отдельным флагом, с ясным объяснением хранения.

## Самостоятельный клиент студента

- Главное меню: «Сегодня», «Завтра», «Неделя», «Сейчас / дальше», «Задания», «Настройки», «Открыть сайт», «Поддержка». Использовать кнопки и короткие сценарии, не требовать знания команд.
- Показывать предмет, время, кабинет, преподавателя, оставшиеся минуты, окна, чётность и изменения «было → стало» со временем правки. При неизвестном кабинете — «Аудитория уточняется». Фильтры группы и подгруппы применяются на сервере.
- Подписки: напоминание за 5/10/15/30 минут (по умолчанию 10), утренняя сводка в выбранное время, изменения ближайших затронутых занятий/подгрупп, дедлайны заданий. Явное согласие, минимум сообщений по умолчанию, тихие часы, пауза `/mute`, отключение и группировка серии правок.
- Общий либо синхронизируемый словарь ru/kk/en. Корректно экранировать динамический текст в выбранном MarkdownV2/HTML; делить длинные сообщения в пределах Telegram API, сохраняя разметку и смысл. Не включать данные других пользователей.
- Поддержка: тип → текст → при необходимости фото → receipt; обращение попадает в ту же очередь, что на сайте, с источником Telegram. Ответ из панели или бота владельца приходит в исходный личный чат. Резервный контакт — `mailto:arappayevv@gmail.com`; ссылка не считается автоматической отправкой письма.
- Локализованный `setMyCommands`: `/start`, `/today`, `/tomorrow`, `/week`, `/now`, `/tasks`, `/settings`, `/site`, `/support`, `/language`, `/unlink`, `/delete_me`, `/help`; `/mute` — быстрый доступ к паузе. Неизвестные команды обрабатывать безопасно.

Inline-режим `@bot` в произвольных чатах и групповые чаты **отложены за обязательный первый выпуск этапа 7Б**. Причины: публичный контекст, дополнительные правила конфиденциальности и ограничения доставки. Будущий `/bind` допустим только по приглашению из панели владельца; участник группы не может назначить чат сам. При реализации включать флагами, дополнить DECISIONS/LIMITATIONS и тесты; сейчас не обещать эти функции пользователю.

## Серверная доставка и ограничения

Нужны серверный scheduler, постоянная outbox/очередь, дедупликация и worker. Таймер страницы не считается доставкой в фоне. Изменение расписания и постановка события в outbox должны согласовываться транзакционно, иначе подтверждённая правка может остаться без уведомления. Ключ доставки включает подписчика, событие/ревизию, вид уведомления и время; повторный webhook/worker не создаёт дубль.

Правила: фильтр затронутых группы/подгруппы и горизонта, выбранные минуты, timezone и quiet hours, объединение близких правок, дедлайны устаревания сообщения. Обрабатывать `429 retry_after`, временные ошибки с ограниченным retry/backoff и запрет дальнейших попыток после блокировки бота пользователем. Начальные ограничения очереди консервативные: около 30 сообщений/с глобально, 1/с в чат и 20/мин в группу; подтвердить актуальные бесплатные лимиты при реализации. Платный broadcast не включать.

После реализации бот обеспечит серверную отправку без открытой вкладки сайта, включая уведомления через установленный Telegram на iOS. Доставка и показ зависят от доступности Telegram, блокировки бота, сети, согласия и настроек ОС; мгновенный показ на каждом устройстве не гарантируется. Пока реальная доставка не проверена, утверждение «работает на закрытом iOS» не публиковать. Web Push сайта остаётся отдельным каналом.

Владельцу: новые обращения, новые/неудачные входы, ошибки публикации/джоб, лимиты и миграции; кнопки открыть панель/ответить/решено/спам с серверной проверкой прав. Группировка всплесков, digest и quiet hours с отдельной политикой критичных сообщений. При недоступности Telegram — серверная почтовая очередь на `arappayevv@gmail.com`; её доставку реализовать и проверить отдельно, не подменять `mailto`.

## Административные действия без обхода owner auth

Привязка владельца начинается **только в уже авторизованной панели с 2FA**. Одноразовый owner-bind код подтверждает связь конкретного owner UID и Telegram user в личном чате. Повтор/другой scope/другой аккаунт/просроченный код отклоняются. Не доверять имени пользователя, присланной роли, chat ID или initData как замене обычной owner авторизации.

Для действий бота нужна отдельная короткая сессия (целевой предел 30 минут), которую сервер выдаёт после свежего подтверждения владельцем через одноразовую HTTPS-ссылку из авторизованной панели с TOTP. Предпочтён этот путь: пароль и TOTP не вводятся в сообщения бота. Отзыв owner-сессий/смена владельца/отвязка немедленно отзывает bot-admin session. Не-владелец не получает админ-данные и не вызывает действия; попытка безопасно игнорируется, без секрета в ответе, и аудируется с ограничением частоты.

Разрешённое меню: `/admin`, разовая замена с мастером группа → дата → пара → поле → preview «было → стало» → подтверждение; кабинет конкретной пары, пары без кабинета, обращения и ответы/статусы, статус сайта и публикации, рассылка с preview/подтверждением/лимитами/журналом. Все callback payload — короткие ссылки на серверное состояние с actor/scope/expiry, не доверенные команды записи.

Удаление группы, массовая замена, полный откат ревизии и другие опасные операции доступны только в панели. «Откатить последнее изменение» в боте означает лишь адресную компенсацию последней разовой правки при совпадении ревизии и отсутствии последующих зависимых изменений; иначе дать ссылку в панель. Не открывать полный rollback под другим названием. После безопасной записи — общий audit с source=telegram и события в общую очередь подписчиков.

## Mini App и раздел панели

Кнопка меню «Открыть» через `setChatMenuButton` открывает канонический сайт. Progressive enhancement: сайт вне Telegram самостоятелен и не загружает `telegram-web-app.js`. В Telegram учитывать themeParams, viewport/safe-area, естественное использование MainButton/BackButton и доступность. Не расширять CSP до wildcard или unsafe-inline; условную загрузку официального скрипта и точные необходимые источники проверить отдельно, сохранить бюджеты и измерить Lighthouse.

`initData` проверяется **на сервере** по официальному алгоритму HMAC, с проверкой `auth_date`, ограниченным TTL и защитой от повторного привязывания/неподходящего контекста. `initDataUnsafe` не источник доверенной личности. Валидный Telegram context подставляет только разрешённые настройки связи; административные endpoint всё равно требуют owner auth с 2FA. Тема, query-параметр и Telegram user не выдают права.

Будущий раздел панели «Telegram»: наличие конфигурации без раскрытия значения, webhook status/последние ошибки, «Проверить подключение», привязка/отвязка владельца, подписчики/группы/доставки/блокировки, defaults и feature flags, quiet hours, рассылки с preview и журналом. Логи минимальны. При отсутствии `TELEGRAM_BOT_TOKEN` бот выключен, сайт работает, панель честно пишет «Telegram не подключён» и показывает инструкцию. Значение токена не возвращается в UI.

## Проверки и gate завершения этапа

- Unit/integration с Telegram API mock: onboarding/настройки/общая временная логика, напоминания/изменения/quiet hours/digest, split/escaping, 429/блокировки/retry, идемпотентность update и доставки.
- Отрицательные HTTP/SQL-тесты: неверный webhook secret/размер/команда, чужой user/chat/обращение, owner без 2FA, истёкшая или отозванная bot-admin session, replay/cross-scope кода, опасная операция из бота. Один chat ID/initData не авторизует администратора.
- Привязка сайт ↔ бот: код одноразовый/10 минут/атомарный; настройки доходят в обе стороны, отзыв действует, локальные задания сохраняются; нет IDOR через device/callback/query.
- Mini App: правильная/поддельная/просроченная initData, тема/safe-area/клавиатура, сайт вне Telegram без SDK. CSP, offline student core, бюджеты JS/CSS и Lighthouse 100/100/100/100 без регрессии; сравнить заранее заданные измерения до/после.
- Secret guard для git/source/build/logs, тесты исключают раскрытие bot/webhook token, initData, чужих chat ID и обращений. Новые таблицы и storage закрыты RLS/grants.
- Владелец отдельно подтверждает реальную связку и доставку, безопасную разовую замену, поддержку, Mini App на iOS/Android и отзыв. Mock-тест не доказывает Telegram/iOS доставку; непроверенное явно остаётся в LIMITATIONS.

Готовность: студент может полностью пользоваться ботом; сайт и бот подхватывают одни настройки; владелец привязывается только из панели с 2FA и выполняет допустимые действия без второго пути авторизации; изменения и обращения едины, аудит и доставка проверены. Без секрета сайт штатно работает. Отчёт этапа содержит schema/functions/webhook, тесты, метрики до/после, риски, инструкции и честный список проверок на устройствах.
