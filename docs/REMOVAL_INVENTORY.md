## Основные зависимости и порядок

1. **Старый каталог — источник работающего продукта.** `scripts/build.mjs` копирует его в отдельный путь и в корень production. Удаление каталога до переноса `app`, `lib`, CSS, manifest, icons и управления сломает оба входа. Сначала перенести нужный код в нейтральную структуру, обновить импорты/сборку, затем удалить старый путь.
2. **ICS зависит от этого исходного пути.** `backend/calendar.mjs:1–2` импортирует библиотеку календаря и времени. При переносе обновить bundle серверной функции, сохранив действующую публичную подписку.
3. **Режим существует также на основном адресе.** Достаточно параметра `?demo=...`; простое удаление отдельного URL не убирает ветвление `S.demo`/`S.mode`, локальную подмену ролей и локальные мутации.
4. **Есть настоящие данные внутри каталога.** Импорт и release snapshot отделены от генератора вымышленных ролей; таблицы и личные данные не удаляются как «демо» по одному имени пути.
5. **Сборка, CI и тесты используют второй маршрут как основной preview URL.** Заменить на закрытый staging/единый маршрут согласованно, сохранив неизменяемый production-base, SHA-256, `release.json`, проверку root и откат.
6. **Протокол PWA удерживает версии старых вкладок.** Старые приложения и второй scope могут оставаться в Cache API даже после новой публикации. Очистка требует отдельной миграции, а не только удаления файлов сервера.

## Service worker / Cache API

- Текущая схема имён: `uniflow:${encodeURIComponent(SCOPE.pathname)}:${VERSION}-static` и `uniflow:${encodeURIComponent(SCOPE.pathname)}:clients`.
- Старый scope создаёт `uniflow:%2Fschedule%2Fbeta%2F:v2-static`, варианты `v3-<hash>-static`/`v4-<hash>-static`, `...:clients`, а также `...:retired-<version>-static` при отсутствии старого shell.
- Метаданные содержат active/install/client pins в URL `.uniflow-worker/active`, `.uniflow-worker/install/<version>`, `.uniflow-worker/client/<id>`. Записи указывают имя кеша, не пароль. Они могут удерживать старый scope и старые root-версии.
- Root-версии `uniflow:%2Fschedule%2F:*` могут содержать собранный код старого режима **даже если в имени нет запрещённого слова**. Удалить/вывести из обращения нужно и такие устаревшие кеши после безопасного обновления, не ограничиваться поиском слова в имени.
- `FILES` перечисляет `app.mjs`, CSS, `lib`, seed/bootstrap, manifest/icons; в старом scope все URL фактически имеют старый префикс. Сама запись `demo.mjs` не обязана быть отдельным precache item: режим встраивается в app и его зависимости.
- Старые service worker registrations продолжают управлять страницами после удаления файлов на сервере. Нужны точечная очистка старого scope/registration и переход с него на единый продукт, а не попытка «удалить базу браузера целиком».
- Сохранённые пользовательские данные в IndexedDB/localStorage не являются Cache API; эти пространства очищаются раздельно.

## Противоречия обязательного «нулевого» guard

1. **Редирект требует знания старого пути/query.** Литералы `/beta/`, `?demo=` нужны в compatibility redirect и его проверке, но буквальный guard запрещает их во всём коде/публичном artifact, кроме двух документов. Нужна явно задокументированная узкая политика для compatibility-реализации и migration tests либо эквивалентный распознаватель без запрещённых raw-строк. Это не основание сохранять режим или переключатель.
2. **Очистка старого хранилища/кешей требует знания старых ключей.** `uf.demo.source.v4`, mode partitions и старый scope нельзя найти и удалить, вообще не распознавая их. Нельзя ради guard удалить весь origin и потерять реальные задания/настройки.
3. **Кеши старых вкладок удерживают прежний app.** Нулевая проверка всех старых Cache API и одновременное сохранение старых pinned shells несовместимы до миграции/перезагрузки всех клиентов. План должен явно вывести старые выпуски из обращения и сохранить личные записи.
4. **История и immutable-архивы содержат прежние имена.** Guard должен проверять актуальное дерево и релиз 1.0, а не требовать удаления всей истории/прошлых immutable releases: это противоречило бы запрету переписывать историю и гарантии отката.
5. **`--no-sandbox` — не режим продукта.** Это флаг запуска headless Chrome в лабораторном Lighthouse. Расширенный семантический поиск отмечает его для проверки; удалять его как пользовательскую песочницу нельзя без анализа CI/browser environment. Точный guard владельца (`beta`/`demo`) этим словом не расширяется автоматически.
6. **Новые документы GAP/PLAN тоже будут временно описывать удаляемое.** Их нельзя забыть при финальном guard: по ТЗ исключения только CHANGELOG и REMOVAL_INVENTORY. Текущий срез ниже уже включает эти документы; после следующих этапов проверку нужно повторить по новому актуальному дереву.
