# Производительность

Цели initial JS ≤60 КБ gzip и CSS ≤15 КБ gzip, точные CSP-хеши, отсутствие тяжёлых runtime/CDN зависимостей. Административный код загружается лениво; расписание не встраивается в исполняемый script.

Production HTML содержит настоящий выбор группы и полный ограниченный публичный снимок в инертном JSON. Поля и аудитория фильтруются до формирования HTML; приватные коллекции, teacher-only задания и закрытые объявления не входят в снимок. Документ ограничен 60 КБ gzip: при превышении снимок целиком остаётся во внешнем bootstrap.json, без обрезания расписания. Ранний ввод и выбранная группа сохраняются при запуске клиента. Перенаправление owner callback выполняется раньше чтения снимка и хранилища.

Модуль приложения — отдельный локальный bundle. При первом посещении маленький загрузчик ждёт first-contentful-paint через buffered PerformanceObserver, затем начинает импорт. Два requestAnimationFrame используются только при недоступности Paint Timing или ошибке подключения observer: сами по себе они не гарантируют доставку записи Performance API. Поиск и подгруппы работают до импорта; обычная отправка формирует ссылку, а после запуска клиента передаётся в очередь подтверждения. Возврат с текущим либо прежним выбором/настройками, приглашение и фоновая вкладка начинают загрузку сразу. Переход в фон во время ожидания также продолжает импорт. Observer и обработчик видимости снимаются. При ошибке импорта форма сохраняет обычную отправку и показывает инструкцию. Это не таймер и не задержка по условию Lighthouse. Обязательный bundle включён в JS-бюджет, даже когда импорт динамический.

После build и budget запустите preview на 4174 и `npm run perf:gate -- http://127.0.0.1:4174/schedule/`. При необходимости задайте `CHROME_PATH` установленного Chrome и `LH_REPORT_DIR` для результатов. Проверка выполняет ровно пять последовательных запусков на свежих профилях. Медианы категорий должны быть 100/100/100/100, медиана LCP ≤1000 мс. Каждый запуск отдельно соблюдает исходные бюджеты Performance ≥95, Accessibility=100, Best Practices ≥95, SEO ≥90 и CLS=0. Ошибка процесса, отсутствующий отчёт и некорректные метрики блокируют проверку. Каждый вызов создаёт новый каталог batch-* с пятью исходными JSON и summary.json, включая неудачные результаты. CI и publisher сохраняют каталог как artifact. Исходные отчёты не заменяются повторным выбором лучшего результата. `npm run perf` оставлен для одного диагностического запуска.

Медиана применяется ко всем пяти заранее заданным результатам, как требует протокол владельца. Добавленный при разработке порог «100 в каждом отдельном запуске» был избыточным: один publisher получил 99 performance при медианах 100/100/100/100 и LCP 783 мс, оставаясь внутри всех исходных бюджетов. Этот отчёт сохранён; прогон не повторялся ради отбора лучшего. Критические индивидуальные бюджеты, 100 Accessibility, нулевой CLS и строгая медиана LCP не ослаблены. Снижение любой медианы либо одного исходного бюджета по-прежнему блокирует публикацию.

Lighthouse [моделирует сеть и CPU через Lantern](https://github.com/GoogleChrome/lighthouse/blob/main/docs/lantern.md). Поэтому наблюдаемое время трассы и simulated LCP нужно записывать отдельно; быстрое наблюдаемое значение не отменяет провал simulated gate. Проверки Paint/Resource Timing выполняются без подмены часов: Playwright clock заменяет getEntriesByName/getEntriesByType пустыми списками.

Прежние числа находятся в архиве и не переносятся как результат новой сборки. Отчёт содержит commit, окружение, все запуски и медиану. Скорость сериализации synthetic fixtures не является измерением throughput БД/API. Физические устройства проверяются отдельно.
