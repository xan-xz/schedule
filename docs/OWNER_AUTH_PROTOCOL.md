# Серверный протокол единственного владельца

Этап1,8ноября2026. Этот документ описывает реализацию и проверенные границы сервера. Само наличие кода/тестов не означает, что владелец уже прошёл настоящий вход или что почтовый провайдер настроен. Факт публикации и реального доступа фиксируется отдельно.

## Идентичность и полномочия

Единственный административный email — arappayevv@gmail.com. Его native Auth UID закрепляется сервером после приглашения; пользовательские metadata, role/email из запроса, старое значениеadmin, Telegram chat_id/initData прав не дают. Проверяется подтверждённая почта, текущая native Auth сессия, её срок, отсутствие блокировки/удаления владельца, AAL2 и именно закреплённый verified TOTP factor. Клиент не выбирает себе фактор или административную личность.

У owner Auth запрещены phone и phone_change. Native SMS/WhatsApp не могут создать почтовое доказательство; MFAphone/OAuth/Web3 AMR не принимаются как password/email/TOTP. Native recovery AMR может подтверждать только свежий email владельца при всех проверках identity/session; он не заменяет независимые password и закреплённый TOTP. Это постоянный серверный инвариант, необходимый при проверке native AMR otp. Первичное создание — только фиксированный email invite; публичная регистрация не создаёт даже owner account без native invited_at. Проверка отложена до конца транзакции: Supabase сначала INSERT, затем записывает invited_at. Email/UID неизменяемы.

## HTTP

`POST /functions/v1/owner-access`, JSON, no-store, CORS только https://xan-xz.github.io; пользовательские токены не являются Supabase JWT. Публичный apikey не заменяет аутентификацию.

| action                            | Назначение / доказательство                                                                                                                                                        |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| status                            | Только available/configured/setupRequired/маскированная почта; без ключей, токенов и внутренних записей                                                                            |
| setup.request                     | Отправить native invite только фиксированному владельцу;15мин окно, общий cooldown/атомарный лимит, не сбрасывать ещё действующее окно                                             |
| setup.start                       | Одноразовая доверенная ссылка/код/native invite proof → короткий opaque challenge; native proof не даёт административной сессии                                                    |
| setup.password                    | Только этот challenge; пароль лично владельца передаётся по HTTPS в Auth, не записывается в БД приложения/логи; fresh password grant и локальное TOTP enrollment при первой настройке; при существующем verified TOTP проверяется текущий пароль без его смены                   |
| setup.verify                      | Проверить новый или закреплённый существующий TOTP; атомарно закрепить фактор/активацию, хеши10recovery-кодов, аудит и сессию; завершить старые admin-сессии                                                     |
| login.begin                       | Проверить пароль через native Auth, отправить отдельное почтовое доказательство, создать5мин challenge                                                                             |
| login.verify                      | Тот же password challenge + fresh email proof + закреплённый TOTP; только после всех факторов сессия. renewRecoveryCodes=true обновляет коды после полной повторной аутентификации |
| recovery.verify / recovery.finish | Пароль + почта + одноразовый hashed recovery code → новая настройка TOTP → fresh AAL2; частично завершённый процесс возобновляется                                                 |
| session.refresh                   | Ротация opaque refresh, native refresh и проверка закреплённой сессии/фактора; reuse отзывает семью, абсолютный срок не продлевается                                               |
| logout / logout.all               | Отзыв app-сессии/всех app-сессий и native Auth сессий; клиент очищает память даже при ошибке сети и честно сообщает неподтверждённый серверный отзыв                               |

Форматы: ow1c. + случайный256битный hex challenge, ow1a. access, ow1r. refresh. Access15мин, абсолютный предел1час. JWT/refresh провайдера остаются на сервере, в зашифрованных AES-GCM состояниях с привязкой к назначению/challenge/native-session. Ключ выводится доменно разделённо из автоматически внедрённого server secret; смена ключа безопасно требует повторного входа, открытого fallback нет. На клиенте только память вкладки, без localStorage/sessionStorage/cookies/URL для app-session.

Bootstrap fragment, появившийся после native email callback, удаляется до асинхронной работы. Доверенная ссылка из письма разбирается как данные: только HTTPS данного проекта и /auth/v1/verify с разрешённым типом; произвольный переданный URL никогда не запрашивается. Native email session хранится как неизменяемое уникальное доказательство, отдельно от заменяемой password session. Одну email session нельзя переиспользовать в другом challenge или после смены password session.

## БД и служебные права

7реляционных таблиц owner_access__: config,challenges,sessions,used_refresh,recovery,attempts,log. Все с RLS/deny-by-default; anon/authenticated не читают их и не исполняют RPC, даже при подставленном клиентском AAL2. Публичный RPC owner_access_command — SECURITY INVOKER, EXECUTE только service_role. Узкие private SECURITY DEFINER helpers проверяют managed Auth без общего SELECT grant на auth._; пустой search_path, квалифицированные имена, клиентским ролям выполнение закрыто. Native Auth получает только права, необходимые двум собственным callback guards.

Соль/хеш прежнего пароля и расписание миграцией не изменяются. Старые admin-токены не должны получать права в обновлённом API; их ограниченный самостоятельный выход сохраняется для безопасного завершения. Дополнительная рольadmin в прежнем account store запрещена триггером и функцией. Успех активации/создания сессии и аудит одной транзакцией: ошибка записи аудита не может скрыть уже выданные одноразовые коды.

Лимиты атомарны, есть прогрессивная задержка и ограничение попыток challenge; IP записывается HMAC-хешем, User-Agent ограничен и очищен. Не логируются пароль, OTP, recovery-коды, provider response, native JWT, body запроса. Закрытый журнал имеет ограничение хранения. Уведомления владельцу через Telegram/email вне auth-писем остаются зависимостью этапа интеграций, доставка не имитируется.

## Проверка и развёртывание

- Перед DDL: приватный snapshot вне репозитория, хеши/счётчики, исходный native Auth users0. Миграция создана CLI и применена штатным Supabase MCP apply_migration; имя локального файла синхронизировано с записанной провайдером версией20261107212017_owner_access. Реальные timetable rows не меняет.
- owner-access-probes.sql запускается только вместе с DDL в BEGIN/ROLLBACK и пустым изолированным Auth baseline. На используемом live-проекте с настоящим владельцем эти probes запрещены даже с ROLLBACK. Синтетические UID/факторы/сессии не являются настоящим логином. Проверяются replay, ACL, native-factor/session revocation, телефон/чужой email, атомарность, expiry/rotation/recovery. Managed supabase_auth_admin нельзя переключить через SQL-коннектор; его callback grants проверены как метаданные, реальный native invite остаётся отдельным тестом.
- owner-access-rollback.sql — только pre-activation rehearsal, с отказом после активации. Сохраняет минимальные запреты регистрации и другой административной личности; не восстанавливает старые пароли/сессии. Проверен rollback→повторное применение внутри внешней откатываемой транзакции.
- Новая функция owner-access выкладывается с verify_jwt=false, поскольку сама проверяет многофакторный протокол/opaque credentials. Старые API обновляются согласованно с UI; гостевое чтение и источник расписания сохраняются.
- SMTP, SiteURL/redirect allowlist и TOTP настройки проверяются отдельно. В текущем подключённом инструменте нет Auth-config API; CUA отклонил Firefox из-за отсутствия URL policy enforcement. Эта граница не обходится чтением токенов браузера/коннектора.
- Настоящий пароль задаёт владелец; реальное письмо/его доставку, положительный вход и физические устройства агент не объявляет проверенными по mock/SQL-результатам.

Будущий Telegram-клиент использует эту идентичность и общие правила доступа. Привязка чата и Mini App initData не заменяют пароль, почту и2FA; короткая bot-admin сессия с узкими действиями — отдельный серверный слой следующего этапа.


При незавершённом setup и одном уже подтверждённом TOTP setup.start возвращает existing-password. setup.password подтверждает текущий пароль и возвращает existing-totp без нового enrollment/QR. setup.verify подтверждает сохранённый фактор на парольной сессии и завершает обычную атомарную активацию. При изменении фактора путь блокируется; пароль и подтверждённый фактор автоматически не заменяются. [Инструкция](OWNER_SETUP_RESUME.md).
