## Дизайн входа и первичной настройки

- Предпочтение существующему Supabase Auth для password hashing и TOTP вместо самописной криптографии. Внедрение — отдельный PR, нынешний custom auth не становится Auth от изменения настроек Dashboard. Актуальные [password auth](https://supabase.com/docs/guides/auth/passwords) и [TOTP](https://supabase.com/docs/guides/auth/auth-mfa/totp) проверяются при реализации.
- Сервер хранит единственный подтверждённый owner UID, связанный с arappayevv@gmail.com. Роль из user_metadata, присланный email/role и одна только успешная регистрация прав не дают. Ограничение продублировано в БД; публичные signup/admin-create закрыты.
- Пароль и TOTP проверяются auth-сервисом; отдельный одноразовый email challenge связывается с той же сессией. До завершения **всех** факторов admin API отказывает. Magic link/OTP сам по себе не должен обходить пароль и2FA.
- Bootstrap:15мин, один раз, только владельцу, без записи ссылки/кода в логи/issue/чат/URL аналитики; после использования уничтожить серверную возможность повторного setup. Прежде чем генерировать настоящий link, должен существовать проверенный consume endpoint и UI, а не открытый административный пароль в env.
- Access15мин; refresh с ротацией, обнаружением reuse и общим revoke. При статическом Pages и отдельном Supabase origin не полагаться на доступность third-party cookies: выбрать проверяемую модель in-memory access/refresh с повторным входом после закрытия вкладки либо реально работающий same-site httpOnly backend. Нельзя обещать httpOnly cookie, если его невозможно выставить на GitHub Pages.
- Recovery-коды — хеши на сервере, однократное использование; показ лично владельцу один раз. TOTP seed/QR не копировать в общие server secrets или инструкции.
- Отключение старых login и выдачи admin-role выполнить согласованно с рабочим setup. После cutover возврат UI не должен возвращать менее строгую авторизацию. Историю git не переписывать.

## Закрытый staging и удаление старых поверхностей

GitHub Pages — публичный хостинг. Не называть отдельный публичный URL закрытым staging. Первый вариант без новой платной инфраструктуры: CI preview на localhost и локальный preview проверенного candidate artifact у владельца. Публичный Actions artifact также не считать секретным; включать только общедоступный static build, никогда секреты/приватный snapshot. Если нужен доступ со смартфона вне локальной сети, сначала реализовать реально защищённый preview, не публиковать приватную админскую сессию.

Сохранить immutable releases, SHA-256, sourceRef и release.json; убрать прежнюю развилку builder. Продвигать точно проверенный artifact, без новой сборки между staging иproduction; record после deploy, fail-closed при ошибке API, безопасный повтор без перезаписи тегов.

В ТЗ есть буквальное противоречие: ноль старых слов в любом файле/кэше и одновременно перенаправления старых URL, миграция их worker/storage и тесты этих URL. Решение: **никакого действующего старого продукта/презентационных данных**, а минимальные compatibility literals учитывать открыто в REMOVAL_INVENTORY/CHANGELOG и отдельном проверяемом manifest. Guard должен отличать разрешённый redirect/retirement/migration и негативный тест от запрещённой ветки приложения. Не обходить проверку конкатенацией или кодировкой слов. Абсолютный byte-zero до завершения compatibility-перехода не заявляется выполненным; список исключений закрытый и проверяемый. Старые аудиты перед финальным guard архивируются вне публичного artifact, актуальная документация переписывается.

Live-настройки, личные задачи/статусы и рабочие именованные шаблоны перенести с проверкой версии и приоритетом уже новых значений. Не делать localStorage.clear/общий IndexedDB delete и не стирать данные соседних сайтов на github.io. Презентационные данные не переносить в рабочие. Старые SW/cache убирать только с доказанным переходом; старый cache-only worker может перехватить навигацию до404, поэтому один 404.html не решает задачу.
