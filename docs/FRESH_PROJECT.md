# Чистый проект Supabase

Это отдельная процедура для нового выделенного проекта. Она не обновляет текущую production-БД и не заменяет личный owner setup. Первичная схема не содержит пароль, verifier, учётные записи, сессии или готовое расписание.

## Воспроизводимая локальная проверка

```sh
npm ci
node scripts/fresh-project-check.mjs
node --test tests/fresh-project.test.mjs
```

Checker всегда создаёт собственную БД PGlite в памяти, последовательно выполняет bootstrap и неизменённые файлы supabase/migrations в порядке имён и закрывает БД. Он не принимает connection string, не читает токены окружения, не обращается к сети и ничего не развёртывает. SHA-256 bootstrap, fixture и каждой миграции выводятся с результатом.

tests/fixtures/managed-auth-schema.sql — только SQL-инфраструктура: роли и три пустые таблицы с нужными полями. Это не GoTrue, не настоящий invite, проверка JWT/пароля, email, TOTP или положительный вход владельца. Fixture никогда не запускается на Supabase. В production эти объекты предоставляет сам провайдер; bootstrap только проверяет их наличие.

## Порядок для действительно нового проекта

1. Использовать новый выделенный Supabase project без пользователей и данных. До процедуры отключить публичную регистрацию и не направлять трафик. Между bootstrap и миграциями не должно появиться Auth-пользователей. Это подготовка изолированного проекта, а не алгоритм online cutover.
2. Проверить проект и backup-политику. Выполнить только backend/fresh-project-bootstrap.sql. Guard откажет до persistent DDL при известных app-объектах, любой обычной public-таблице/view/sequence, истории миграций или существующих Auth-пользователях; пустая таблица тоже считается существующим проектом. Управляемые extension-owned relations определяются через pg_depend/pg_extension и исключаются. Проверяется и старый group_schedule, но новая схема его не создаёт.
3. Применить существующие файлы supabase/migrations в порядке версий штатным Supabase migration tooling. Не менять их содержимое, не придумывать более старую baseline-версию и не вставлять/исправлять schema_migrations вручную. Bootstrap — явно документированная отдельная baseline-процедура, а не якобы исторически применённая миграция.
4. Настроить и развернуть серверные функции согласованно с публичной конфигурацией. Проверить grants/RLS, URLs, Email/SMTP и TOTP, затем лично пройти owner setup. SQL-проверка не отправляет приглашение и не задаёт пароль.
5. Пустой uf_platform содержит только валидные пустые массивы, revision 1; uf_signal также revision 1. Настоящее расписание загружается отдельным проверенным импортом с ID/provenance/счётчиками/checksum. Никакие прежние учебные записи не подставляются автоматически.

В схеме остаются восемь compatibility-таблиц, необходимые существующим неизменяемым миграциям и активному writer: schedule_settings, schedule_sessions, schedule_login_attempts, uf_platform, uf_signal, uf_accounts, uf_sessions, uf_versions. Credential/session/account-таблицы пусты. uf_commit выполняет CAS и сохраняет предыдущую версию; владельца создаёт отдельный многофакторный протокол.

Базовый клиент обновляет публичные данные polling-запросами. Этот минимальный bootstrap не создаёт managed realtime publication и не добавляет в неё таблицы; uf_signal доступен только для чтения ревизии. Подключение Realtime при необходимости проверяется отдельно и не является условием replay существующих миграций.

После ошибки не пытаться повторным bootstrap «починить» частично созданный проект: guard намеренно откажет. Разобрать причину и продолжить только штатными отслеживаемыми миграциями либо заново подготовить действительно пустой изолированный проект. Автоматического DROP, cleanup существующих пользователей и migration repair здесь нет.

Обычный db reset с одними текущими upgrade-миграциями не является самостоятельным fresh bootstrap. Для локального CI предусмотрен этот checker; реальная установка всегда начинается с явно указанной baseline-процедуры. Исторические setup-файлы удалены из текущего дерева после успешной репетиции. Единственная инструкция новой установки — этот документ и guarded bootstrap; действующая БД не менялась. Старые значения в истории Git не являются действующими доступами, история не переписывалась.
