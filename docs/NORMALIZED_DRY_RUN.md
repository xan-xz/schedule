# Локальная проверка нормализованного хранилища

Это проверка foundation, а не переключение API или рабочего расписания. CLI не читает env, не подключается к БД, не отправляет запросы и не изменяет исходный файл. Новая схема `uniflow_data` проверяется отдельно; `uf_platform`, текущий writer и native Auth не затрагиваются.

## Входные данные и отчёт

Запускать из корня репозитория на Node.js версии, указанной в `package.json`:

```powershell
node scripts/normalized-dry-run.mjs --fixture 100x40
node scripts/normalized-dry-run.mjs --input C:/private/platform-backup.json --revision 5 --report C:/private/normalized-report.json
```

Поддерживаются исходный объект расписания с массивами `groups` и `lessons`, строка `{revision,data}` либо backup с `uf_platform: {id,data,revision,updated_at}`. Массив из одной строки также допустим. Из backup берётся только `uf_platform.data`: `uf_signal`, `group_schedule`, `uf_versions` и остальные поля не переносятся. Без `--revision` используется revision строки; для исходного объекта и synthetic — 1. Override должен быть положительным безопасным целым числом JavaScript.

CLI выполняет `decomposePlatform → recomposePlatform`, проверяет полное равенство JSON и canonical SHA-256 через `platformChecksum`. Отчёт в stdout и необязательном `--report` содержит только фиксированные счётчики, revision, checksum и локальные длительности. Имена групп, содержимое уроков, пути и значения секретов в отчёт не включаются. Ошибки также выводятся как JSON с кодом без фрагментов входного файла. `databaseExecuted:false` означает, что CLI не выполнял SQL; локальный round-trip не доказывает успешный импорт в PostgreSQL.

Fixture `100x40` содержит ровно 100 синтетических групп и 4000 занятий, по 40 на группу. Это данные для проверки масштаба, не данные студентов и не обещание времени ответа API. Fixture намеренно не проходит через ограничение старого редактора на 3000 занятий.

## SQL с обязательным ROLLBACK

```powershell
node scripts/normalized-dry-run.mjs --input C:/private/platform-backup.json --sql C:/private/normalized-private.sql --report C:/private/normalized-report.json
node scripts/normalized-dry-run.mjs --fixture 100x40 --sql C:/private/normalized-synthetic.sql --report C:/private/normalized-synthetic-report.json
```

Каталог назначения должен существовать. Все выходные файлы создаются через `wx`: существующие файлы, каталоги и ссылки не перезаписываются. Совпадающие пути входа/выхода и двух выходов отклоняются. После успешного запуска для повторения нужны новые имена файлов. Предварительная проверка предотвращает обычную частичную запись; при гонке файловой системы первый новый файл может остаться, но существующий файл не будет перезаписан. Режим `0600` запрашивается при создании; на Windows размещайте SQL и backup в каталоге с закрытым ACL.

**Для `--input` SQL содержит полный snapshot, а результат SQL — полный `normalized_export`.** Это приватные артефакты: не включайте их в Git, публичные отчёты или логи CI. `--report` не содержит snapshot. В отчёте сохраняются SHA-256 пакета SQL, прочитанных DDL и probes, позволяющие установить точную версию проверки.

Для `--fixture 100x40` пакет использует компактный серверный генератор `backend/normalized-load-fixture.sql`: он создаёт тот же DTO из `generate_series`, а не пересылает многомегабайтный литерал через Management API. Полное равенство DTO с JavaScript-генератором проверяется в CI, включая порядок и подгруппы. Реальный входной файл всегда передаётся без такой замены.

Скрипт включает входной snapshot ровно один раз в dollar-quoted литерале со случайным разделителем. Он удаляет только проверенные внешние `begin;`/`commit;` исходной миграции и формирует один пакет:

1. `BEGIN`, timeout 180 секунд, текущая foundation DDL.
2. Одна временная fixture, однократный импорт и SQL probes.
3. Итоговый SELECT с `normalized_export`, `probeSummary`, пятью `groupReadTimings` и `groupReadExplain`.
4. `ROLLBACK`.

DDL намеренно отказывает, если схема `uniflow_data` уже существует; инструмент не удаляет и не переиспользует существующую схему. Запускайте пакет целиком в изолированном PostgreSQL либо согласованной staging-транзакции с нужными ролями `service_role`, `anon`, `authenticated`. При ошибке runner должен выполнить `ROLLBACK` в `finally`; не заменяйте его на `COMMIT`. CLI ничего не исполняет автоматически.

## Что проверяет SQL

`backend/normalized-probes.sql` проверяет допустимый snapshot и отклонение закрытого manifest, повторяющихся root keys и collection manifest, undeclared record, forged `sourceId`, `indexes`, `groupIds`, derived slot и переставленных derived positions. Для проверки перестановки нужны минимум два элемента; меньшая коллекция помечается `passed:null` с причиной, а не как успешная проверка.

В новой staged-схеме попытка записать несуществующий кабинет в урок должна завершиться `23503`; внутренний subtransaction отменяет эту попытку. Проверяются RLS и отсутствие клиентских прав на все 20 таблиц, а также реальное выполнение RPC/helper под `service_role` и отказ под `anon`/`authenticated`. Второй импорт под service role обязан дойти до guard `normalized_import_already_initialized`. Если runner не может переключить роль, соответствующая проверка имеет `passed:null,tested:false`; это не подтверждение доступа роли. Native Auth и роли Auth-admin не используются.

После `ANALYZE` выполняются пять чтений уроков для первых пяти групп, затем один `EXPLAIN (ANALYZE,BUFFERS,FORMAT JSON)` для той же формы запроса. Длительности измеряются `clock_timestamp()` внутри БД; это последовательные локальные чтения после импорта, не HTTP, не cold-start и не SLA. Для fixture 100×40 каждое чтение должно вернуть 40 строк. Последняя проверка требует, чтобы экспорт полностью совпал с исходным snapshot после всех probes.

После SQL runner должен передать `normalized_export` в `recomposePlatform`, затем сравнить исходный JSON и `platformChecksum` ещё раз. PostgreSQL `jsonb::text` имеет другой формат сериализации: его SHA-256 нельзя сравнивать с canonical checksum адаптера. Результаты из Node REPL с отдельным realm перед проверкой можно нормализовать через `JSON.parse(JSON.stringify(result))`; обычному Node CLI это не требуется.

Эти проверки не включают API cutover, конкурентный рабочий writer, UI редактирования, production rollout или подтверждение реального owner login. Они должны оцениваться отдельно.

## Выполненная проверка

`tests/normalized-sql.test.mjs` запускает настоящий PostgreSQL в WASM через dev-only PGlite. Зависимость не входит в браузерную сборку. В CI выполняются DDL с нуля, 18 SQL-проверок с настоящим переключением client/service-role, точный roundtrip, Unicode-порядок производных справочников, отказ отката после активации и повторное применение схемы. Отдельно тот же SQL-пакет проверяет 100 групп × 40 занятий; весь пакет заканчивается ROLLBACK.

На hosted PostgreSQL 17 также выполнены оба пакета с откатом: исходный снимок 19/524/54/133 и синтетические 100/4000, по 18 успешных проверок без пропуска ролей. Пять чтений по 40 занятий дали 1,140 / 0,429 / 0,459 / 0,414 / 0,447 мс (медиана 0,447 мс); это тёплое чтение внутри БД, не задержка пользовательского API. После проверки новая схема отсутствовала, рабочая revision осталась 5, SHA-256 совпал. Пакет с многомегабайтным литералом до этого был отклонён лимитом размера Management API; компактный генератор устранил ограничение транспорта.

Схема пока **не установлена постоянно и не является источником записи**. Текущий API всё ещё использует прежний документ и лимит 3000 занятий. Следующий этап требует атомарного cutover, адресных revisions/rollback и проверки конкурентных правок, а не объявления миграции законченной по результатам этого dry-run.
