# Security

## Кандидат этапа 1 · 8 ноября 2026

Owner-only вход реализован в новом коде; его production-развёртывание и настоящий вход владельца **не подтверждены этим документом**. Source SHA, CI, SQL, версии функций, Pages и origin smoke фиксируются в итоговом отчёте этапа в outputs. Исторические секции ниже описывают выпуск 6–7 ноября, включая прежний PBKDF2/password-only auth; они не являются текущим контрактом нового owner endpoint.

- Единственный owner email `arappayevv@gmail.com`, закреплённый native Auth UID и утверждённый проверенный TOTP-factor. Сервер не принимает роль из user_metadata, присланные email/role или Telegram chat ID как право доступа.
- Native invite только на фиксированный адрес, проверенное одноразовое email proof в 15-минутном окне UniFlow, личная установка пароля и native TOTP до активации. Supabase Auth хранит bcrypt-хеш пароля; локальный QR не передаётся внешнему сервису. Разовый список из 10 recovery-кодов, в БД только хеши. [Хранение паролей Supabase](https://supabase.com/docs/guides/auth/password-security).
- Обычный вход требует password proof, отдельное свежее email proof и TOTP той же серверной цепочки. Native JWT сначала проверяется Auth `/user`; затем проверяются issuer/audience/expiry/owner/session/AMR. Email-session ID используется один раз и не заменяет password-session. Native TOTP должен повысить исходную сессию до AAL2.
- Auth identity только email: триггеры запрещают непустые `phone`/`phone_change`, изменение email/UID и регистрацию без разрешённого owner invite. Проверка invite отложенная: native Auth сначала INSERT, затем присваивает invited_at в той же транзакции. API и SQL дополнительно проверяют отсутствие телефона. AMR `otp` без этого инварианта не доказывает email; SMS/WhatsApp/OAuth не служат email proof.
- Дополнительный admin запрещён и API, и БД. Старые admin login/password-change и legacy save в кандидате возвращают 410; старые административные токены не читают/пишут данные, разрешён только self-logout. При owner activation прежние admin-сессии отзываются, дополнительные старые admin-аккаунты деактивируются.
- App access token — случайный opaque 256-битный, срок 15 минут; refresh с ротацией/reuse detection, абсолютный предел 1 час. В БД хеши opaque credentials; provider access/refresh — AES-GCM state с привязкой к purpose. В браузере credentials только в памяти, без localStorage/IndexedDB/SW cache и без обещания httpOnly cookie на Pages. Auth fragment немедленно очищается из URL; вставленная email-ссылка только разбирается по точному project origin/path, никогда не загружается как произвольный URL.
- Каждая защищённая операция повторно проверяет app session и действующую native `auth.sessions`/owner/TOTP-factor/AAL2. Выход, native revoke, смена factor и сроки закрывают доступ; refresh не продлевает абсолютную границу. Отказ сервера не мешает локальному выходу, но UI не объявляет отзыв других устройств подтверждённым.
- Recovery требует пароль, свежее email proof и один резервный код; до подтверждения нового native TOTP административная сессия не выдаётся. Повтор временно прерванной recovery возобновляет состояния, не расходуя код повторно. Обновление кодов доступно после обычного полного входа; публичного сброса забытого пароля после активации нет.
- Атомарные challenge/lease/rotation RPC, лимиты 15 запросов/IP и 60/scope за 15 минут, предел попыток challenge и ограниченная прогрессивная задержка. Закрытый audit с HMAC IP и ограниченным device text, без request bodies/паролей/OTP/QR/tokens; activation/success audit в одной транзакции. Автоматические Telegram/email оповещения ещё не подключены.
- Таблицы owner access закрыты RLS/grants; public RPC — SECURITY INVOKER, пустой search_path, EXECUTE только service_role. Узкие private SECURITY DEFINER helpers возвращают лишь owner UID/результат проверки Auth session, без blanket SELECT на auth и без чтения паролей.

Подготовлены отрицательные provider/mock/HTTP/UI тесты, 21 SQL-проба с ROLLBACK и rehearsal отката/повторного применения до активации. Расписание сохранено: revision 5 / 19 групп / 524 занятия, архив revision 3. Приватный backup 338022 байта с ограниченным ACL находится вне workspace; SHA-256 и точные результаты — в отчёте/manifest, не вместе с публичными данными. Выполнение реальной защищённой ролью supabase_auth_admin, native email delivery, owner login и физические устройства не проверены. После активации нельзя возвращать старый password-only вход обычным rollback.

Auth Dashboard config остаётся отдельным gate. CUA остановился из-за неподдерживаемого контроля URL в Windows Firefox; авторизация Dashboard не установлена. Не считать настройки изменёнными или пользователя разлогиненным. [Настройки и секреты](docs/SECRETS_SETUP.md), [инструкция владельца](docs/ADMIN_ACCESS.md), [ограничения](docs/LIMITATIONS.md). ## Проверено 6 ноября 2026

Клиент содержит только публичный publishable key Supabase. Секретный ключ и действующие пароли в текущих файлах не найдены. Проверены 18 достижимых коммитов, 32 уникальных текстовых blob: обнаружен старый клиентский SHA-256-проверочный хеш админского пароля (`89a0f0d:index.html:60` и восемь следующих коммитов). Он удалён из текущей версии раньше этой работы, но остаётся в истории. Хеш допускает офлайн-перебор; нельзя считать прежний пароль секретным.

Если действующий пароль повторяет старый, владелец должен сменить его через сервер после выполненного обновления либо через приватную панель Supabase, затем завершить сессии обеих версий. Не публиковать новый пароль или его хеш в issue/коммите/чате. При обнаружении служебного ключа ротировать ключ в Supabase и обновить секрет Edge Functions. Очистку истории можно выполнить отдельно согласованным `git filter-repo`; эта работа не переписывает историю и не делает force push. Клоны, кеши и форки могут сохранять старые данные даже после очистки.

Read-only проверка работающего проекта подтвердила RLS на `group_schedule`, `schedule_settings`, `schedule_sessions`, `schedule_login_attempts`, `uf_platform`, `uf_accounts`, `uf_sessions`, `uf_signal`, `uf_versions`. Клиентские роли имеют SELECT только на открытые `group_schedule` и `uf_signal`. Административные таблицы клиенту недоступны. Оба административных endpoint активны с `verify_jwt=false`: это необходимо для существующих непрозрачных сессий, а не замена серверной проверки.

## Историческая модель выпуска 6 ноября 2026

- Пароли: PBKDF2-SHA256, соль на аккаунт, 210000 итераций. Сессионные токены — случайные 256 бит, в БД только SHA-256, срок 2 часа; клиентские токены не должны сохраняться на диск.
- Сервер проверяет роль и принадлежность занятия каждому запросу. Преподаватель может отменить/перенести собственную пару; смена предмета/преподавателя требует администратора. У гостя и студента нет серверной записи.
- Отметка посещаемости требует действующего занятия с учётом чётности и отмены. Сервер дополнительно проверяет группу/подгруппу активного студента.
- Импорт не может добавить разрешённые отпечатки конфликтов. Разрешены только уже сохранённые исходные пары; изменённые записи не получают прежнее исключение. Импорт не удаляет молча связанные аккаунты, задания, объявления, посещаемость и запросы.
- `logout.all` завершает все сессии текущей личности; для встроенного `admin` — и старые сессии «Пары». Смена пароля и отзыв обеих разновидностей сессий выполняются одной транзакцией. Проверка хеша при выдаче сессии блокирует гонку входа со сменой пароля.
- Развёрнут атомарный лимит входа: 10 попыток/IP и 30/имя аккаунта за 15 минут, общий для обоих серверов; 450–600 мс задержки на ошибку входа. В журнале лимитера только SHA-256 с префиксами, без открытых IP/логинов. Лимит по имени также позволяет отказ в обслуживании конкретному аккаунту; это сознательный компромисс малой системы.
- Служебные RPC имеют `SECURITY INVOKER`, пустой search_path и EXECUTE только `service_role`.

Advisors: performance/health без замечаний; security содержит только 7 INFO «RLS без policy» на закрытых служебных таблицах — это ожидаемый deny-all для клиента. Не добавлять публичные policy ради удаления этой информационной подсказки. [Описание проверки Supabase](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).

После подтверждённого продвижения UniFlow в основной путь включён архивный режим schedule-admin v3: проверенная старая сессия получает 410 при сохранении с адресом нового редактора; до таблицы запись не доходит. Старые данные и гостевое чтение сохранены. Откат статического root сам по себе не включает старую запись: для неё нужен согласованный возврат авторитетного источника и явный LEGACY_WRITES_ENABLED=true с повторным серверным деплоем. Пароли и сессии при включении архивного режима не менялись.

## Границы защиты и известные ограничения

- Статический GitHub Pages поддерживает CSP через meta, но не политику HTTP-заголовков `frame-ancestors`/HSTS. DOM-оболочка должна использовать textContent для пользовательских строк; старый staff-интерфейс использует экранированные HTML-шаблоны и не считается полностью переведённым на DOM.
- CORS ограничивает браузеры, но не является проверкой прав. Проверку выполняют сессия/роль и RLS. Защищать forwarded IP нужно настройкой управляемого шлюза; не доверять произвольному прокси.
- Открытое расписание и справочники (включая опубликованные имена преподавателей) публичны. Личные задания и прогресс на общем устройстве доступны следующему пользователю браузера. Не сохранять в офлайн-кеш аккаунты, посещаемость, токены, защищённые ответы или полную админскую версию.
- Исторический общий JSON ограничен 2 MB и 3000 записей на раздел; все группы конкурируют за одну ревизию. Откат восстанавливает весь документ, включая задания и посещаемость, а не одну выбранную запись. Аккаунты не откатываются.
- У старого endpoint собственная модель и таблица; эта ветка не объединяет живые данные молча. См. `docs/DATA.md`.
- Фоновые Web Push, WebAuthn, распределённая защита от ботов и загрузка файлов не реализованы. TOTP MFA для владельца реализована в кандидате этапа 1, с границами проверки выше; не переносить это утверждение на WebAuthn или реальную доставку. Напоминания при закрытом приложении доступны через календарный ICS fallback с ограничениями календаря.
- Не логировать тела запросов, пароли, токены, ФИО/посещаемость. В эту работу не добавлена аналитика или трекеры.
